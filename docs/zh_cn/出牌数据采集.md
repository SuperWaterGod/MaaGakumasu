# 出牌数据采集

当前提供两种模式：正在运行的 MFA 可用只读 ADB 旁路采集；beta 的 Agent 可启用操作事件采集。现有出牌策略保持原样。

## Agent 操作事件采集

将采集版本部署到测试包的 `agent/`，并在测试包的 `config/decision_capture.json` 写入：

```json
{
    "enabled": true,
    "match_cards": true,
    "console_summary": true,
    "console_details": true,
    "reward_preview": true,
    "reward_identity_cache": true,
    "max_bytes": 2147483648,
    "min_free_bytes": 536870912
}
```

配置不存在或 `enabled` 不为 `true` 时关闭。培育开始/继续时读取配置，创建一个整次培育的采集分段；同次培育的多场出牌共用该目录。未进入培育会话的调用（例如偶像之路）仍按每次 `ProduceCardsAuto` 创建独立目录。已启动的 Python Agent 不会因复制代码自动更新，需要在任务安全结束后重新加载 Agent。

### 整次培育会话与路线记录

Agent 使用 MaaFramework 的 Context/Tasker 事件监听接口观察现有流水线，监听器本身不新增游戏输入。奖励候选详情采集由单独的条件动作执行，启用时增加预览点击与截图，最终领取仍沿用原选择；其余路线和出牌策略保持原样。需要带事件监听接口的 MaaFramework Python 包；接口不可用时输出日志并继续任务。

- 进入实际培育循环 `ProduceEntry` / `ProduceEntryNIA` 时才建立 `session_id`、启动采集和后台分析；`started_at` 与 `gameplay_started_at` 同时从该入口计时。`Produce` 是任务入口，`ProduceLoop` 是准备/次数循环，`ProduceStart` 是点击主界面培育，均不单独建会话。准备期间仅在内存中暂存各准备节点最近一次截图与识别证据，进入培育后写入同一分段，并保留 `observed_at`；最多缓存五个节点。准备期间停止或完成后进入下一轮准备但未正式开局，不生成空会话、采集目录或后台进程。
- 各场出牌、路线节点和结算事件都带会话 ID；每场出牌另有 `battle_id`，每个采集分段有独立 `run_id` / `segment_id`。考试重试仍在同次会话内。任务启动、准备启动时间分别保存为 `task_started_at`、`preparation_started_at`，不计入正式培育跨度。报告的 `wall_seconds` 为含中断等待的会话跨度，不当作纯操作时间；已有旧记录若包含 `gameplay_started_at`，报告按该时间统计并保留原 `recorded_session_started_at`，不修改原会话证据。
- 中断、任务提前结束和 Agent 正常退出关闭当前分段，保留按控制器 UUID 隔离的续跑索引。「继续培育」或「跳过准备阶段」且配置偶像/歌曲、剧本、难度相同时沿用 ID；配置不一致、新开始培育或索引不可读时创建新会话。配置一致不是游戏存档身份的独立证明；进程被强制结束后可能有漏采，报告保留缺口。
- 会话绑定配置偶像/歌曲、初/NIA、难度、属性偏好与任务节点设置；偶像识别成功时另存原始 OCR 身份和相似度。资源版本、卡库、偶像数据、出牌模型、培育流水线和采集代码 SHA-256 按分段保存，跨版本续跑不覆盖旧版本证据。
- `deck_id` 是本次培育的牌组观测标识。准备/出牌画面中读到的牌名和路线候选分别保存；尚未确认完整开局库存、张数和改造，不把所有出现过的候选当作持有牌组。偶像/玩家等级仅在准备画面明确显示对应标签时读取，未展示则为未知；难度单独绑定。
- 奖励选牌、跳过、商店折扣候选/购买/兑换/容量不足、强化选牌/确认、删除/复制/变换选牌/确认都有 `route_before`、`route_input_result` 和后续 `route_after`。保留节点的全部原识别结果、任务覆盖参数、候选截图、实际点击位置与框、框架执行状态。下一次成功的图像识别提供后续画面；`DirectHit` 不产生新截图，不用其旧缓存当作操作后观察。
- 后台独立进程对路线原图 OCR，严格匹配可见完整卡名，保留全屏 OCR 和显式价格证据。只有带 Pt/ポイント 等单位、与唯一牌名同一行的价格才关联成本；裸数字、歧义价格、未解析的饮料/道具与不可读候选继续保留原图和未知字段。`actual_cost`、库存变化和 `game_action_confirmed` 尚未独立确认，不以框架点击成功推断扣费/获得/强化/删除成功。点击与牌名的几何对应仅标为 `geometry_only`。
- 结算生成/完成节点点击前保存画面，并读取明确标签后的最终评价点、评级和 Vo/Da/Vi；重复或冲突的值保留证据，不强填数值。返家、失败终止与中断原因分别记录；返家本身不是得分或考试通过的独立证据。

会话清单保存为 `debug/produce_sessions/<session_id>/session.json`，各分段原始事件仍在 `debug/decision_capture/<run_id>/`。生成跨分段报告：

```powershell
python tools/report_produce_session.py D:/Projects/MaaGakumasu-beta/debug/produce_sessions/<session_id>
```

输出 `report.md` / `report.json`，关联各路线的候选、价格证据、选择输入、后续画面、准备及结算观测，并列出丢弃事件、关联缺口和未完整采集的分段。`complete` 仅表示所观察流水线事件的覆盖条件满足，不代表候选库存、持有牌组或动作效果已经全部确认。后台分析未开启/尚未完成时可先看原始证据，分析完成后重新生成报告。

已有多轮完整实机采集数据；2026-10-15 去除 Pillow 后的新一轮记录 17 个奖励页、62 个候选，恢复/领取输入完整，后台零异常、零丢弃。此前在主界面入口或结束后的准备阶段产生的短会话作为历史记录保留，不计为完成轮次；正式建会话现已延迟至实际培育循环，停止、续跑及连续多轮行为通过本地回归和 AgentServer 内存控制器验证，尚需下一轮实机核对。价格、强化/删除确认和结算结构化字段仍需按采集报告逐项补齐。

停止收尾按已保存的任务 ID 关联，不在任务结束回调中反向查询控制器。后台 OCR 的原生逐帧调试日志默认关闭；识别证据和异常继续保存在派生 JSON、`status.json` 和 `analysis.log`。

记录内容：进入/退出观察、YOLO 全部候选及手牌区域过滤标记、推荐/单牌/超时选牌原因、选中框、两次底层点击、饮料任务、跳过、移动卡牌与确认弹窗、返回可操作状态或退出后的截图。两个点击归属于同一个逻辑操作。

出牌与监听器截图直接复用框架图像；奖励预览通过当前任务控制器截图，全部按 BGR 转 RGB 后保存，不旋转。主数据统一为竖屏 720×1280；异常宽高比保留实际尺寸并标注，不强行旋转，奖励探查在不支持的尺寸下跳过。检测置信度不是卡牌收益。`decision_after.game_action_confirmed` 暂为 `null`，返回可操作状态不能独立证明牌已打出。

存在本地技能卡库时，默认同时启动独立的卡牌分析进程。它只读取截图与事件，使用没有物理输入能力的离线 Maa 控制器执行检测/OCR，不向 MuMu 发送操作。`match_cards: false` 可关闭后台分析。采集与分析异常各自记录，不阻塞培育。

默认将后台摘要回传到 MFA 控制台。同一次操作的前后信息合为一条 `<details>/<summary>` 折叠日志，在操作后画面分析完成时输出，标题显示连续操作编号、操作类型、所选牌名和耗时，例如 `操作 4｜出牌：精神統一+｜6.4秒`。展开后显示选择依据、操作前状态与 Buff、手牌、观察到的变化和原始采集索引。折叠内容分为操作前、手牌和观察变化；状态分短行，Buff 每行最多两项，分数变化单独显示增减量，其他变化每行最多两项。手牌使用 `1｜`、`2｜` 编号，避免 HTML/Markdown 将其重新解释为有序列表；操作后不重复列整手牌；使用饮料不显示无关手牌。`→` 标记选中牌，`荐` 标记游戏推荐，`禁` 标记不可用，`≈` 标记前缀匹配，未知牌单独提示。内容先做 HTML 转义，换行使用 `<br/>`，分区间保留空行，整个块在一条物理日志中发送，避免 MFA 拆行后只显示标题。单行通知照常显示，完整信息仍保存在 JSON。

“操作 1、2、3…”每个出牌采集会话从 1 开始，只计出牌、饮料、跳过等逻辑操作，不是回合数。原 `seq` 计所有事件，包括两次点击、弹窗及观察，所以出牌前 #9、点击 #10/#11、操作后 #12 都属于同一次操作；这些原始编号仍在展开后的“采集索引”以及事件/派生 JSON 中保留，不重编号。派生索引和日志通知新增 `console_operation_number` 用于对应展示编号。

合并标题的耗时是操作前记录到操作后观察的单调时钟间隔，包含点击及等待，不含后台 OCR 分析延迟。启用采集控制台且后台已启动时，原独立“出牌耗时”行降为调试日志，避免重复；未启用或后台未启动时保留原输出。缺少后帧、识别失败或未确认 HUD 会明确提示，前后可读数值没有变化时也保留该操作，不把它解释为没有效果。

`console_details: false` 可恢复逐行输出，每行都带日志级别及 `[对局采集]` 前缀，适用于不支持折叠的旧客户端或纯终端。当前 beta 的 MFA 源码版本 `1080d3e1500f3439ac896ab2eca9aeb8e885f1f4` 已核对原生 HTML 折叠支持：[Agent 日志转 Markdown](https://github.com/MaaXYZ/MFAAvalonia/blob/1080d3e1500f3439ac896ab2eca9aeb8e885f1f4/MFAAvalonia/Extensions/MaaFW/AgentHelper.cs#L915)、[DetailsParser 转为 Expander](https://github.com/MaaXYZ/MFAAvalonia/blob/1080d3e1500f3439ac896ab2eca9aeb8e885f1f4/Markdown.Avalonia.Html/Core/Parsers/DetailsParser.cs)。`analysis_console.jsonl`、事件及派生 JSON 仍保存完整内容，折叠只影响控制台展示。

解析会稍晚于实际操作，合并日志须等待后帧；状态变化不等于已经确认动作成功。`console_summary: false` 可关闭摘要。已加载旧采集代码的 Agent 需要在本轮结束后重新启动客户端，新清单信息和独立耗时行的调整才会生效；独立识别进程在下一场出牌启动时读取新识别代码。

每场出牌退出前，最多等待 3 秒让最后一条操作摘要完成控制台输出，正常顺序为“最后一条操作 → 未检测到体力 → 退出出牌 → 后续演出事件”。已经输出时立即继续；关闭摘要或没有记录操作时不等待。后台退出、采集失败或手动停止时提前结束等待；超时时提示摘要尚未输出，保留后续补发和完整派生记录，不无限等待分析。

### 奖励候选详情采集（测试中）

奖励确认节点接入 `ProduceRewardConfirm`，在原策略已经选中候选、尚未领取时采集详情。`reward_preview` 默认为 `true`，仅在整次培育采集启用并成功建立会话后生效；设置为 `false` 可关闭额外预览。原有“跳过饮料”分支直接保留。当前适配 720×1280 单行奖励页，已有两轮 37 张确认截图覆盖三项饮料和四项技能卡；其他布局或高亮不明确时不探查，领取按钮必须重新确认。

通过图标边框、等间距排列和外侧橙色选中括号定位候选，不逐张搜索大型图标库；被角标打断的边框仍需视觉证据才能补齐。先保存已选项详情，再依次单击其他项；高亮、候选位置、领取按钮和连续两帧详情稳定均需核对，每次等待最长 1.8 秒。所有探查结束后重新点回原选择，同时核对高亮和原详情画面，再调用单独的 `ProduceRewardReceive` 领取。探查、恢复和领取分别记录；点击失败时先尝试恢复，恢复不明确则停止任务，不领取其他项。手动停止后不再发出恢复或领取点击。

OCR 在独立后台进程执行，分名称、消耗和效果 ROI 保存完整证据。`reward_<seq>.json` 包含候选框、牌名及卡库身份、可见效果原文、卡头明确显示的有符号数值、详情核对状态；卡头消耗不等于实际扣费。未匹配技能卡的饮料/道具保留名称和效果原文，类型标为 `other_or_unknown`。详情画面没有确认刷新时，保留截图与 OCR 证据，但不把上一项名称和效果归给新候选。

奖励识别默认走「名称 → 结构化库」：技能卡使用 `produce_skill_cards.json`，饮料/P 道具使用 `produce_reward_items.json`。两个库固定在相同上游提交，数据 SHA 进入会话清单与分析签名。饮料保留 `actions`，P 道具保留 `effects`、模式和强化标记；同名记录无法唯一确定时不随意挑第一项。同步命令为 `python tools/sync_reward_items.py`，默认跟随当前技能卡库的提交，不在游戏运行时联网。

名称精确命中且库效果非空时只 OCR 名称，直接载入结构化 DSL，标为 `catalog_default`；`identity.effective_effect_dsl` 此时表示标准版本的默认效果，`effective_effect_confirmed=false`，不宣称定制或临时变化已核对。卡头没有单独 OCR 时其数值为空，牌库的通用消耗 `cost` 不强转为体力或实际扣费。名称索引使用字典，已解析身份复用，不逐次遍历整个卡库。详情面板像素完全一致时复用先前结果，名称也不重复 OCR。

名称未知、额外强化标记、库效果为空、显式定制提示或同名详情画面改变时，才追加效果和消耗 OCR。已观察到变化的当前效果保留待核对状态，数据库参考 DSL 与画面原文分开保存。首见卡牌没有可用定制提示时，牌库结果仍只是标准版本假设；图标相同不能证明定制状态相同。

新奖励观察使用 schema_version=2，不再用正文正则生成 `effects.structured`。`semantic_status` 区分 `catalog_default`、`ocr_text_only` 和 `unverified_detail`；正文兜底只保存 `visible_text`、完整 OCR 证据与截图，不推断条件或收益。库内空效果（如「はつぼしブレスレット」）也保留原文待核对。旧采集的结构化正文解析作为历史证据保留，不覆盖。

`reward_identity_cache` 默认为 `true`，可单独关闭。后台从本采集分段内已经核对的详情学习图标身份，最多保留 128 个条目；比较图标内部并包含角标和强化标记，不搜索上游图标大全。只有身份唯一、图标差异很小、库效果非空且没有兜底/定制提示时，非原选项可以跳过预览点击。原选项始终先核对实际高亮和稳定详情；新图标、冲突、版本不符或缓存不可用时仍点击预览。缓存命中事件标记 `observation_method=icon_cache`，当前详情没有打开，因此 `detail_verified=false`；身份经当前图标核对标为 `identity_verified=true`，效果仍是牌库默认。发生过预览点击时仍须恢复并核对原选择再领取；全部复用时记录原选择保持。手动停止和诊断重试约束保持不变。

旧数据可直接回放保存的 OCR，不重新截图、识别或操作设备：

```powershell
python tools/replay_reward_effects.py D:/Projects/MaaGakumasu-beta/debug/decision_capture/<run_id> --database D:/Projects/MaaGakumasu-beta/data/produce_skill_cards.json
python tools/report_produce_session.py D:/Projects/MaaGakumasu-beta/debug/produce_sessions/<session_id>
```

回放只接受已关闭且 OCR 完成的采集，核对原卡库版本、事件及来源结果 SHA，输出独立的 `derived/reward_effects/<analysis_id>/`；原始事件、原 OCR 结果和当时的控制台日志不覆盖。新回放同时使用原图和已保存的 OCR 来验证减重路径，报告 `estimated_roi_requests` 与可复用图标次数；不重新做 OCR，不将估算当作旧运行中实际省掉的点击或耗时。会话报告自动关联同一 OCR 分析版本的最新回放，并汇总效果来源状态。新运行的后台进程自动执行名称查库和原文留存，分析签名包含图像接口及缓存代码。奖励日志区分画面原文和牌库默认，显示候选识别数与图标复用数，不把复用身份称为当前详情核对通过。

原事件增加 `reward_page_start`、`reward_preview_input`、`reward_candidate_preview`、`reward_selection_restored`、`reward_page_end` 和 `reward_receive_input`。每页通过 `reward_page_id` 关联原策略选择与领取确认节点；`report.json.reward_pages` 汇总每项派生详情、探查完整性、原选择、恢复及领取输入，Markdown 报告增加“奖励候选详情”。探查完整性仅针对实际检测到的候选；不能据此声称已读取隐藏效果或获得全部候选。

控制台将每个奖励页合为一条 `[奖励采集]` 折叠日志，在记录领取点击后输出，标题为“奖励选择 N｜所选牌名｜选择依据”。展开后按图标从左到右列出候选及效果原文，`→` 标记最终选择，同时显示领取按钮点击结果、详情覆盖数及原选择恢复情况。编号在本采集分段连续递增。原选项先采集、其他候选随后探查的真实事件顺序保持不变；显示层按位置排序，不再逐项输出或夹入“已保存详情”通知。选择节点的提示改为“已选择…”，不会提前声称奖励已领取。

标题已包含选择策略，展开后不再重复“选择依据”。每个候选只标一次“牌库默认”，显示层对数据库的常见数值、条件、触发、次数和修正作有限中文格式化；重复执行的动作显示“元气＋10（共2次）”，不合并成未经验证的总收益。未知 DSL 显示“特殊效果（详见数据记录）”，不把内部函数名、英文标识和花括号直接写到用户界面。此处只格式化库数据，不恢复 OCR 正文规则解析、不改变选择策略或结构化结果；完整原始 DSL 继续保存在 JSON 中。

领取动作完成后，最多等待 3 秒让本页后台摘要输出；摘要已就绪时立即继续，避免最后一项摘要落到下一条路线事件之后。分析关闭时输出领取点击结果，分析超时则明确提示后台摘要稍后补发。领取失败、恢复失败、预览缺项、任务中断和缺少领取记录分别呈现，按钮点击成功仍不代表库存变更已独立确认。

切换选中项后的核对使用本页初始候选框，比较图标内部内容与外侧橙色括号，不再反复拟合可能被高亮打断的边框。候选内容明显改变时拒绝继续。预览超时、点击失败或观察异常增加 `reward_preview_wait_diagnostic`：保存首次异常及最后观察的截图、预期/实际布局、高亮分数、图标差异、按钮是否检查、详情稳定/刷新/恢复差异、等待次数、用时及分项原因。正常成功预览不额外保存诊断截图；单次失败等待最多增加两张，重复图片继续按 SHA-256 去重。

只有仍选中其他候选、参考图标行可核对且领取按钮可见时才允许额外单击一次，记录 `reward_preview_retry`；目标已经选中但详情不稳定、候选内容变化、底层输入失败或手动停止均不重试。恢复原选择只执行一次，未核对成功仍停止领取。`reward_page_end.failure_diagnostic` 保留导致缺项的原因，报告每页增加 `diagnostics` 和 `retries`，日志展开内容显示失败候选、分项原因与尝试次数。未知值不补成成功或零。

## 当前任务的 ADB 旁路采集

在仓库中使用已安装的 Python、MaaFramework、OpenCV 和 NumPy。OpenCV 仅供该开发者旁路工具检测画面，不属于用户运行依赖，不需要新增 LLM 服务。先用 `adb devices -l` 确认设备，仅指定一个实例：

```powershell
python tools/capture_battle.py --adb D:/MuMuPlayer-12.0/nx_main/adb.exe --serial 127.0.0.1:16384 --output D:/Projects/MaaGakumasu-beta/debug/decision_capture --resource D:/Projects/MaaGakumasu-beta/resource/base
```

仅执行 `exec-out screencap -p`，不发送点击、不另建游戏控制器。默认每 1.5 秒观察，体力和跳过按钮同时匹配时保存出牌帧，并保留短暂过渡帧。第一帧用于诊断；出牌动画或特殊界面可能漏采。

ADB 截图在写盘时统一缩放到 720×1280，记录来源尺寸与是否缩放；旧版本已保存的设备原分辨率截图保留。`battle_hint` 是模板判断，不能直接作为可信场景标签。横屏或不兼容布局不会强行旋转匹配。

旁路采集默认从资源包的 `data/produce_skill_cards.json` 读取卡库；`--database` 可指定其他路径。`--no-card-analysis` 仅采集画面。独立分析使用本地 MaaFramework 和框架必需的 NumPy；用户运行链不依赖 Pillow。

默认运行上限一小时，连续十五分钟未发现出牌场景时停止；连续三次截图失败或达到写盘限制也停止。每次采集的 `observer.json` 包含 PID 与停止文件路径，在该目录创建空文件 `STOP` 即可停止。`observer_status.json` 提供最新采样时间、原始尺寸和匹配结果。

## 战斗状态识别

每帧派生结果的 `battle_state` 保存剩余回合、本人分数、体力、元气、当前 Vo/Da/Vi 属性及倍率。每个字段包含数值、置信度、ROI 和原 OCR；不是当前第几回合，未知时也不填零。剩余回合使用完整圆盘区域和收窄数字区域两种 OCR 视图，记录 `value_views`；有效数值冲突时保持未知，避免动画线条把 `1` 误读成 `61`。元气也使用两个数字区域，兼容盾牌/数字的位置变化，不强行截取 OCR 中的数字后缀。若无法确认出牌 HUD，整帧状态标为未知。NIA 本人分数根据随排名移动的唯一宽白边框定位，不使用头像、偶像名、栏内颜色或固定第一名位置作为本人依据；旧粉色兜底已移除。边框缺失或存在多个候选时保持未知。目前没有单独输出名次数字，也未分别验证“初”等其他培育的分数布局，不能将现有 NIA 几何规则宣称为全部剧本已适配。

可见 Buff 使用统一列表记录类型、数值、单位、持续时间和图标/OCR 证据，支持后续扩展不同流派。当前已有截图模板覆盖好印象、集中、干劲、好调、绝好调、消耗体力减少/增加、得分提升/降低、低下状态无效和热意。持续回合、剩余次数、百分比按不同格式解析，不将其混成普通层数。好调和绝好调分别读取 `goodConditionTurns` / `perfectConditionTurns`；灰色好调图标只确认图标身份，没有读到回合数时不会推断为 0。模板匹配到图标但数值不清楚时记录 `icon_only`，数值保持未知；未注册区域记录 `candidate_region`，不声称区域一定存在 Buff。隐藏、滚动和其他流派的新图标仍需采集验证；`buffs_complete` 当前始终为 `false`。

非凡的“冰火”指强气/温存姿态，不是体力消耗减少/增加 Buff。当前姿态单独记录在 `battle_state.anomaly`：包含 `stance`、`stance_stage`、`full_power_charge`、`next_stance`、`transition_after_turns` 的值与证据；顶层 `stance` 保留基础姿态兼容字段。支持已有截图里的强气、温存、全力和通常图标，一/二阶段独立识别，不从缺失图标推断通常。全力值区域显示文字或两个数字视图冲突时保持未知。指针预告仅在匹配到蓝色预告图标时读取明确的 `Nターン後`；没有预告不代表下一回合不切换。`pointer_condition` 只保存“累計5↑”“変更回数1↑”等条件文字，不把其中的数字当作当前累计全力值或实际切换次数。`held_cards_count` / `held_cards_capacity` 从明确的“保留 N/M”读取，两个视图冲突或缺失时保持未知；数量不代表已确定保留牌的具体身份。剩余出牌次数、累计计数、保留牌身份和のんびり姿态尚未解析。

姿态和指针预告模板分别登记在 `stances` / `stance_previews`，与 Buff 模板共用原生匹配接口和来源校验。热意从可见图标读取数值与持续回合，不根据预告或卡库反推。已追加一轮全力主轴样本，用于检查蓄积/进入/退出循环和保留数量；它不代表全力策略已完成或各偶像均验证。后续补跑按 [出牌状态采样计划](出牌状态采样计划.md) 的机制缺口安排。

感性好调样本也出现了指针及集中增长预告，因此指针本身不能用来判定非凡流派。感性的指针条件和效果目前尚未结构化；好调效果提升百分比、P 道具及卡片专属触发图标也仍有缺口，不能由基础好调回合数代替。

集中/干劲代表样本已追加。集中效果提升独立保存为 `concentrationEffectBuffPercent`（百分比）和 `duration`（明确读到的持续回合），来源依据 `精神統一+` 的 `setConcentrationEffectBuff(0.2,3)` 与操作后 20%、2 回合图标核对；后续重复使用的截图出现 40%。这不等于获得集中的数量增幅，也不等于某张卡的单次集中倍率。干劲、好印象等其他百分比图标的获得量/效果子类型尚未逐项核实，继续保存未知区域及截图，不仅凭基础图标推断语义。

Buff 与非凡姿态定位复用 MaaFramework 原生 `TemplateMatch`，配置登记在 `assets/data/battle_buff_templates.json`，素材在 `assets/resource/base/image/produce/buffs/`。模板由已有 MuMu 12 日文 NIA、720×1280 截图直接裁切为 56×56，不旋转或缩放；背景、变化的数字和时间文字涂为 RGB `(0,255,0)`，使用 `green_mask: true`。当前选择 `method: 10001`（反转归一化平方差）以保留图标颜色差异，阈值与跨类别歧义间隔见登记表。匹配区域限制在各自的左侧 HUD 区域，按实际匹配框定位旁边 OCR，避免匹配到卡牌角标。

登记表保存来源会话、截图 SHA、裁剪区域、掩码、生成图片 SHA，以及图标含义的交叉核对依据。例如 `仕切り直し` 的 `halfCostTurns+=4` 与随后出现的蓝色减耗图标关联，`キラメキ` 的 `doubleCostTurns+=2` 与红色增耗图标关联；这不是仅凭颜色猜测，也不代表已通过游戏弹窗逐项确认。不同模板在同一位置分数接近时保留未知；多个数字视图冲突时不强行赋值，只有一个视图读到有效数字时采用该值。普通层数图标若读到百分比、回合或次数文字，记录 `value_unit_conflict`，避免把集中效果提升等复合图标当作集中层数。此前的颜色类别模板不再作为默认 Buff 识别后端。

好调图标依据 `振る舞いの基本` / `アドリブ` 的好调效果与截图核对；绝好调依据 `魅惑のパフォーマンス` 的 `perfectConditionTurns+=3` 与操作后的 3 回合图标核对，均保留尚未通过弹窗确认的标记。同一种 Buff 的亮色/灰色模板不互相制造歧义；不同含义的候选仍比较匹配间隔。好调/绝好调候选若同时读到百分比，记录单位冲突并保持未知，避免把好调效果提升图标当作基础持续回合。Buff 和姿态在同一位置竞争时，如果 Buff 有相近或更强证据，姿态记录 `conflicts_with_buff_icon` 并保持未知，避免将好调误报为温存。

对登记为同一 `value_family` 的普通集中/集中效果提升图标，只有一个明确数值格式（整数或百分比）时才用该格式区分候选，证据保存在 `value_format_disambiguation`。数值格式同时出现或缺失时保留原有图标歧义规则；与其他图标的竞争仍按匹配间隔处理。该规则不会将任意带百分比的未知图标自动命名为集中效果提升。


Maa YOLO 定位手牌后，对卡牌底部名称做 OCR；Agent 采集优先复用当时检测框，旧的旁路截图在离线分析时重新检测。名称做 NFKC 和空白/标点归一化，保留 `+`，再匹配对应基础/强化条目。

多卡重叠时，同时检查原名称区域和按右侧相邻卡牌收窄的可见区域。完整卡库名称已出现且尾部只混入一至两个字符时，允许清理相邻文字。牌名被截断时，在存在遮挡证据、可见前缀至少三个字符且覆盖候选名称至少 60% 时，匹配最相近候选；基础版与强化版按同名归组。如果多个不同牌名共享可见前缀，则仅保留相似度候选，不因其中一个名称更短就确认身份。原 OCR、匹配依据和两种区域的结果全部保留。

基础牌名识别独立于强化信息：前缀匹配或遮挡区域未读到 `+` 时，仍给出基础牌名，强化状态保留未知，不阻塞基础身份使用。不同区域若指向不同卡名则保持未知；若卡名相同而强化标记不一致，则标记牌名已匹配、强化待确认，不把多余 `+` 静默丢弃。当前采集优先覆盖牌名和状态，强化解析为后续收益计算保留证据。

- 输出卡牌 ID、原名、流派、强化标记、OCR 置信度、名称相似度、备选条目和 `reference_effect_dsl`。
- OCR 置信度不足、前缀过短或候选接近时返回未知，不强制选一个 ID。名称相似度与前缀覆盖程度都不是校准后的概率。
- `++` 等额外标记记录为 `base_match_variant_unresolved`，可给出基础强化条目，但不把额外变化当作已解析效果。
- 自定义改造与局内临时变化尚未从画面解析，因此 `effective_effect_dsl` 保持未知；卡库效果只是参考，不能当作当下实际收益。
- 当前上游名称以日文为主；汉化名需提供经过核对的 `data/skill_card_aliases.json`（仓库布局为 `assets/data/`），结构为 `{"卡牌source_id": ["别名", "别名+"]}`。升级版别名应填在升级条目的 ID 下。未覆盖汉化名保持未知，不自动翻译后强行匹配。

对已采集的旧数据补做匹配，不修改原始事件：

```powershell
python agent/produce/analysis.py --capture-dir D:/Projects/MaaGakumasu-beta/debug/decision_capture/<run_id> --resource D:/Projects/MaaGakumasu-beta/resource/base --database assets/data/produce_skill_cards.json
```

分析结果按卡库、模型、匹配代码与 Maa Python 包版本区分目录。`index.jsonl` 将事件 ID 与结果文件关联；`status.json` 包含进度、匹配/未知数量和错误。运行期间使用 `--follow` 持续读取新增事件；采集关闭后处理完现有事件即结束。采集器定期更新心跳，在路线/事件阶段等待下一场出牌时分析进程继续等待；没有新事件超过两分钟且采集心跳失效时才结束。

采集素材均位于 Git 忽略的 `debug/` 内，应保留，不能作为源代码提交。后续识别结果应另存派生数据，保留原始观测。

### 运行链图像处理

采集、后台分析与奖励图标缓存统一使用 BGR NumPy 数组，`agent/utils/image_io.py` 封装 MaaFramework 原生 PNG 编解码和缩放。只对符合竖屏比例的截图归一化到 720×1280，不自动旋转；旧 PNG 原图仍可读取。培育业务统一归入 `agent/produce/`；奖励预览、缓存、读取集中在 `rewards.py`，查库集中在 `catalog.py`；出牌与奖励日志在 `console.py` 统一维护，后台入口为 `analysis.py`。目录划分及后续拆分标准见 [开发相关](开发相关.md) 和根目录 `AGENTS.md`。

图标缓存版本提升为 2，使用原生缩放的 64×64 BGR 缩略图；旧版本 1 的 Pillow 缩略图不参与匹配，重新识别后学习，不放宽匹配阈值。历史缓存及原图不批量删除。原生 PNG 压缩体积可能较大，仍受原有采集空间上限约束；维护工具和构建图标工具可独立使用 Pillow。
