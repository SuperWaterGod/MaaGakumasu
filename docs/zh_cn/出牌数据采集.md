# 出牌数据采集

当前提供两种模式：正在运行的 MFA 可用只读 ADB 旁路采集；beta 的 Agent 可启用操作事件采集。现有出牌策略保持原样。

## Agent 操作事件采集

将采集版本部署到测试包的 `agent/`，并在测试包的 `config/decision_capture.json` 写入：

```json
{
    "enabled": true,
    "match_cards": true,
    "console_summary": true,
    "console_details": true,
    "max_bytes": 2147483648,
    "min_free_bytes": 536870912
}
```

配置不存在或 `enabled` 不为 `true` 时关闭。每次进入 `ProduceCardsAuto` 读取配置，创建一个独立采集目录。已启动的 Python Agent 不会因复制代码自动更新，需要在任务安全结束后重新加载 Agent。

记录内容：进入/退出观察、YOLO 全部候选及手牌区域过滤标记、推荐/单牌/超时选牌原因、选中框、两次底层点击、饮料任务、跳过、移动卡牌与确认弹窗、返回可操作状态或退出后的截图。两个点击归属于同一个逻辑操作。

截图直接复用框架图像，按 BGR 转 RGB 后保存，不旋转。主数据统一为竖屏 720×1280；异常宽高比保留实际尺寸并标注，不强行旋转。检测置信度不是卡牌收益。`decision_after.game_action_confirmed` 暂为 `null`，返回可操作状态不能独立证明牌已打出。

存在本地技能卡库时，默认同时启动独立的卡牌分析进程。它只读取截图与事件，使用没有物理输入能力的离线 Maa 控制器执行检测/OCR，不向 MuMu 发送操作。`match_cards: false` 可关闭后台分析。采集与分析异常各自记录，不阻塞培育。

默认将后台摘要回传到 MFA 控制台。同一次操作的前后信息合为一条 `<details>/<summary>` 折叠日志，在操作后画面分析完成时输出，标题显示连续操作编号、操作类型、所选牌名和耗时，例如 `操作 4｜出牌：精神統一+｜6.4秒`。展开后显示选择依据、操作前状态与 Buff、手牌、观察到的变化和原始采集索引。状态与属性、同帧的 Buff 行会合并，操作后不重复列整手牌；使用饮料不显示无关手牌。`→` 标记选中牌，`荐` 标记游戏推荐，`禁` 标记不可用，`≈` 标记前缀匹配，未知牌单独提示。内容先做 HTML 转义，换行使用 `<br/>`，整个块在一条物理日志中发送，避免 MFA 拆行后只显示标题。单行通知照常显示，完整信息仍保存在 JSON。

“操作 1、2、3…”每个出牌采集会话从 1 开始，只计出牌、饮料、跳过等逻辑操作，不是回合数。原 `seq` 计所有事件，包括两次点击、弹窗及观察，所以出牌前 #9、点击 #10/#11、操作后 #12 都属于同一次操作；这些原始编号仍在展开后的“采集索引”以及事件/派生 JSON 中保留，不重编号。派生索引和日志通知新增 `console_operation_number` 用于对应展示编号。

合并标题的耗时是操作前记录到操作后观察的单调时钟间隔，包含点击及等待，不含后台 OCR 分析延迟。启用采集控制台且后台已启动时，原独立“出牌耗时”行降为调试日志，避免重复；未启用或后台未启动时保留原输出。缺少后帧、识别失败或未确认 HUD 会明确提示，前后可读数值没有变化时也保留该操作，不把它解释为没有效果。

`console_details: false` 可恢复逐行输出，每行都带日志级别及 `[对局采集]` 前缀，适用于不支持折叠的旧客户端或纯终端。当前 beta 的 MFA 源码版本 `1080d3e1500f3439ac896ab2eca9aeb8e885f1f4` 已核对原生 HTML 折叠支持：[Agent 日志转 Markdown](https://github.com/MaaXYZ/MFAAvalonia/blob/1080d3e1500f3439ac896ab2eca9aeb8e885f1f4/MFAAvalonia/Extensions/MaaFW/AgentHelper.cs#L915)、[DetailsParser 转为 Expander](https://github.com/MaaXYZ/MFAAvalonia/blob/1080d3e1500f3439ac896ab2eca9aeb8e885f1f4/Markdown.Avalonia.Html/Core/Parsers/DetailsParser.cs)。`analysis_console.jsonl`、事件及派生 JSON 仍保存完整内容，折叠只影响控制台展示。

解析会稍晚于实际操作，合并日志须等待后帧；状态变化不等于已经确认动作成功。`console_summary: false` 可关闭摘要。已加载旧采集代码的 Agent 需要在本轮结束后重新启动客户端，新清单信息和独立耗时行的调整才会生效；独立识别进程在下一场出牌启动时读取新识别代码。

采集器使用有界后台队列保存文件。达到体积/磁盘限制或写盘失败时停止采集，游戏任务继续；丢弃及错误写入清单。进程异常退出可能留下未完成目录，不能视为完整对局。

## 当前任务的 ADB 旁路采集

在仓库中使用已安装的 Python、Pillow、OpenCV 和 NumPy。它们来自当前开发/框架环境，不需要新增 LLM 服务。先用 `adb devices -l` 确认设备，仅指定一个实例：

```powershell
python tools/capture_battle.py --adb D:/MuMuPlayer-12.0/nx_main/adb.exe --serial 127.0.0.1:16384 --output D:/Projects/MaaGakumasu-beta/debug/decision_capture --resource D:/Projects/MaaGakumasu-beta/resource/base
```

仅执行 `exec-out screencap -p`，不发送点击、不另建游戏控制器。默认每 1.5 秒观察，体力和跳过按钮同时匹配时保存出牌帧，并保留短暂过渡帧。第一帧用于诊断；出牌动画或特殊界面可能漏采。

ADB 截图在写盘时统一缩放到 720×1280，记录来源尺寸与是否缩放；旧版本已保存的设备原分辨率截图保留。`battle_hint` 是模板判断，不能直接作为可信场景标签。横屏或不兼容布局不会强行旋转匹配。

旁路采集默认从资源包的 `data/produce_skill_cards.json` 读取卡库；`--database` 可指定其他路径。`--no-card-analysis` 仅采集画面。独立分析使用本地 MaaFramework、NumPy 和 Pillow；beta 的内置 Python 已补齐 Pillow。

默认运行上限一小时，连续十五分钟未发现出牌场景时停止；连续三次截图失败或达到写盘限制也停止。每次采集的 `observer.json` 包含 PID 与停止文件路径，在该目录创建空文件 `STOP` 即可停止。`observer_status.json` 提供最新采样时间、原始尺寸和匹配结果。

## 输出与报告

保存位置为运行包的 `debug/decision_capture/<run_id>/`：

- `manifest.json`：模式、版本、限制、状态、丢弃数和未知字段。
- `events.jsonl`：带顺序、时间、关联操作 ID 的事件。
- `frames/`：PNG 原图，按 SHA-256 去重。
- `derived/card_identity/<analysis_id>/`：每帧手牌、OCR 证据、卡库匹配、事件关联索引与处理状态。
- `report.md` / `report.json`：事件数量、缺帧、操作配对和未知项。

旁路结束时自动生成报告；Agent 记录或仍在运行的目录可生成阶段报告：

```powershell
python tools/report_decision_capture.py D:/Projects/MaaGakumasu-beta/debug/decision_capture/<run_id>
```

当前已加入牌名、卡库身份、可见强化标记和战斗状态识别。未识别字段保持未知。现有自动逻辑的操作不等于最优策略标签。没有完整路线和开局信息时，不宣称已还原完整培育。

## 战斗状态识别

每帧派生结果的 `battle_state` 保存剩余回合、本人分数、体力、元气、当前 Vo/Da/Vi 属性及倍率。每个字段包含数值、置信度、ROI 和原 OCR；不是当前第几回合，未知时也不填零。剩余回合使用完整圆盘区域和收窄数字区域两种 OCR 视图，记录 `value_views`；有效数值冲突时保持未知，避免动画线条把 `1` 误读成 `61`。元气也使用两个数字区域，兼容盾牌/数字的位置变化，不强行截取 OCR 中的数字后缀。若无法确认出牌 HUD，整帧状态标为未知。NIA 本人分数根据随排名移动的唯一宽白边框定位，不使用头像、偶像名、栏内颜色或固定第一名位置作为本人依据；旧粉色兜底已移除。边框缺失或存在多个候选时保持未知。目前没有单独输出名次数字，也未分别验证“初”等其他培育的分数布局，不能将现有 NIA 几何规则宣称为全部剧本已适配。

可见 Buff 使用统一列表记录类型、数值、单位、持续时间和图标/OCR 证据，支持后续扩展不同流派。当前已有截图模板覆盖好印象、集中、干劲、好调、绝好调、消耗体力减少/增加、得分提升/降低、低下状态无效和热意。持续回合、剩余次数、百分比按不同格式解析，不将其混成普通层数。好调和绝好调分别读取 `goodConditionTurns` / `perfectConditionTurns`；灰色好调图标只确认图标身份，没有读到回合数时不会推断为 0。模板匹配到图标但数值不清楚时记录 `icon_only`，数值保持未知；未注册区域记录 `candidate_region`，不声称区域一定存在 Buff。隐藏、滚动和其他流派的新图标仍需采集验证；`buffs_complete` 当前始终为 `false`。

非凡的“冰火”指强气/温存姿态，不是体力消耗减少/增加 Buff。当前姿态单独记录在 `battle_state.anomaly`：包含 `stance`、`stance_stage`、`full_power_charge`、`next_stance`、`transition_after_turns` 的值与证据；顶层 `stance` 保留基础姿态兼容字段。支持已有截图里的强气、温存、全力和通常图标，一/二阶段独立识别，不从缺失图标推断通常。全力值区域显示文字或两个数字视图冲突时保持未知。指针预告仅在匹配到蓝色预告图标时读取明确的 `Nターン後`；没有预告不代表下一回合不切换。`pointer_condition` 只保存“累計5↑”“変更回数1↑”等条件文字，不把其中的数字当作当前累计全力值或实际切换次数。`held_cards_count` / `held_cards_capacity` 从明确的“保留 N/M”读取，两个视图冲突或缺失时保持未知；数量不代表已确定保留牌的具体身份。剩余出牌次数、累计计数、保留牌身份和のんびり姿态尚未解析。

姿态和指针预告模板分别登记在 `stances` / `stance_previews`，与 Buff 模板共用原生匹配接口和来源校验。热意从可见图标读取数值与持续回合，不根据预告或卡库反推。已追加一轮全力主轴样本，用于检查蓄积/进入/退出循环和保留数量；它不代表全力策略已完成或各偶像均验证。后续补跑按 [出牌状态采样计划](出牌状态采样计划.md) 的机制缺口安排。

感性好调样本也出现了指针及集中增长预告，因此指针本身不能用来判定非凡流派。感性的指针条件和效果目前尚未结构化；好调效果提升百分比、P 道具及卡片专属触发图标也仍有缺口，不能由基础好调回合数代替。

集中/干劲代表样本已追加。集中效果提升独立保存为 `concentrationEffectBuffPercent`（百分比）和 `duration`（明确读到的持续回合），来源依据 `精神統一+` 的 `setConcentrationEffectBuff(0.2,3)` 与操作后 20%、2 回合图标核对；后续重复使用的截图出现 40%。这不等于获得集中的数量增幅，也不等于某张卡的单次集中倍率。干劲、好印象等其他百分比图标的获得量/效果子类型尚未逐项核实，继续保存未知区域及截图，不仅凭基础图标推断语义。

Buff 与非凡姿态定位复用 MaaFramework 原生 `TemplateMatch`，配置登记在 `assets/data/battle_buff_templates.json`，素材在 `assets/resource/base/image/produce/buffs/`。模板由已有 MuMu 12 日文 NIA、720×1280 截图直接裁切为 56×56，不旋转或缩放；背景、变化的数字和时间文字涂为 RGB `(0,255,0)`，使用 `green_mask: true`。当前选择 `method: 10001`（反转归一化平方差）以保留图标颜色差异，阈值与跨类别歧义间隔见登记表。匹配区域限制在各自的左侧 HUD 区域，按实际匹配框定位旁边 OCR，避免匹配到卡牌角标。

登记表保存来源会话、截图 SHA、裁剪区域、掩码、生成图片 SHA，以及图标含义的交叉核对依据。例如 `仕切り直し` 的 `halfCostTurns+=4` 与随后出现的蓝色减耗图标关联，`キラメキ` 的 `doubleCostTurns+=2` 与红色增耗图标关联；这不是仅凭颜色猜测，也不代表已通过游戏弹窗逐项确认。不同模板在同一位置分数接近时保留未知；多个数字视图冲突时不强行赋值，只有一个视图读到有效数字时采用该值。普通层数图标若读到百分比、回合或次数文字，记录 `value_unit_conflict`，避免把集中效果提升等复合图标当作集中层数。此前的颜色类别模板不再作为默认 Buff 识别后端。

好调图标依据 `振る舞いの基本` / `アドリブ` 的好调效果与截图核对；绝好调依据 `魅惑のパフォーマンス` 的 `perfectConditionTurns+=3` 与操作后的 3 回合图标核对，均保留尚未通过弹窗确认的标记。同一种 Buff 的亮色/灰色模板不互相制造歧义；不同含义的候选仍比较匹配间隔。好调/绝好调候选若同时读到百分比，记录单位冲突并保持未知，避免把好调效果提升图标当作基础持续回合。Buff 和姿态在同一位置竞争时，如果 Buff 有相近或更强证据，姿态记录 `conflicts_with_buff_icon` 并保持未知，避免将好调误报为温存。

对登记为同一 `value_family` 的普通集中/集中效果提升图标，只有一个明确数值格式（整数或百分比）时才用该格式区分候选，证据保存在 `value_format_disambiguation`。数值格式同时出现或缺失时保留原有图标歧义规则；与其他图标的竞争仍按匹配间隔处理。该规则不会将任意带百分比的未知图标自动命名为集中效果提升。

可重新生成相同截图模板与预览：

```powershell
python tools/build_buff_templates.py --capture-root D:/Projects/MaaGakumasu-beta/debug/decision_capture --preview debug/buff_green_templates_preview.png
```

上游图片子仓库 [gakumas-tools/gk-img](https://github.com/gakumas-tools/gk-img/tree/1c0907223dcd9da1754aa435a50b893f4fc0f11f/docs/skill_cards) 包含 WebP 技能卡图标和详情图；本次核对的图标文件为 96×96 整卡缩略图，不是 56×56 的独立 HUD Buff 素材。可以用 Pillow 读取 WebP、提取角标、按比例重采样并保存为 PNG，但描边、压缩和游戏 HUD 裁剪可能不同，转换后仍需实机截图验证；本次启用素材全部来自已有截图。

`index.jsonl` 的操作后记录增加 `decision_id` 和 `state_changes`，只比较两帧都确认的字段。该变化可能同时包含回合结算、P 道具触发和动画，不全部归因于选中卡；`game_action_confirmed` 仍为未知。后台状态统计包含可读状态帧、各字段覆盖数、Buff 后端/模板列表和独立的状态识别错误数；识别代码、登记表与经过校验的 PNG 素材都参与 `analysis_id`。模板缺失或校验失败时明确记录错误，数值采集和培育继续。

## 技能卡数据库与身份匹配

`assets/data/produce_skill_cards.json` 独立于偶像歌曲卡库，保存上游原始字段、效果 DSL、提交 SHA、文件校验值及抓取时间。本次快照包含 908 条记录（含强化版），来自 `gakumas-tools/gakumas-tools`；再分发声明在同目录 `GAKUMAS_DATA_LICENSE.txt`。

更新时显式指定经过核对的上游提交，不在培育中自动联网更新：

```powershell
python tools/sync_skill_cards.py --revision <40位上游提交SHA>
```

Maa YOLO 定位手牌后，对卡牌底部名称做 OCR；Agent 采集优先复用当时检测框，旧的旁路截图在离线分析时重新检测。名称做 NFKC 和空白/标点归一化，保留 `+`，再匹配对应基础/强化条目。

多卡重叠时，同时检查原名称区域和按右侧相邻卡牌收窄的可见区域。完整卡库名称已出现且尾部只混入一至两个字符时，允许清理相邻文字。牌名被截断时，在存在遮挡证据、可见前缀至少三个字符且覆盖候选名称至少 60% 时，匹配最相近候选；基础版与强化版按同名归组。如果多个不同牌名共享可见前缀，则仅保留相似度候选，不因其中一个名称更短就确认身份。原 OCR、匹配依据和两种区域的结果全部保留。

基础牌名识别独立于强化信息：前缀匹配或遮挡区域未读到 `+` 时，仍给出基础牌名，强化状态保留未知，不阻塞基础身份使用。不同区域若指向不同卡名则保持未知；若卡名相同而强化标记不一致，则标记牌名已匹配、强化待确认，不把多余 `+` 静默丢弃。当前采集优先覆盖牌名和状态，强化解析为后续收益计算保留证据。

- 输出卡牌 ID、原名、流派、强化标记、OCR 置信度、名称相似度、备选条目和 `reference_effect_dsl`。
- OCR 置信度不足、前缀过短或候选接近时返回未知，不强制选一个 ID。名称相似度与前缀覆盖程度都不是校准后的概率。
- `++` 等额外标记记录为 `base_match_variant_unresolved`，可给出基础强化条目，但不把额外变化当作已解析效果。
- 自定义改造与局内临时变化尚未从画面解析，因此 `effective_effect_dsl` 保持未知；卡库效果只是参考，不能当作当下实际收益。
- 当前上游名称以日文为主；汉化名需提供经过核对的 `data/skill_card_aliases.json`（仓库布局为 `assets/data/`），结构为 `{"卡牌source_id": ["别名", "别名+"]}`。升级版别名应填在升级条目的 ID 下。未覆盖汉化名保持未知，不自动翻译后强行匹配。
