# 培育数据库与素材更新

“一键培育”最前面的“更新数据库和素材”默认不勾选。安装包提供初始数据库；勾选该任务可更新技能卡、饮料、P 道具与支援卡数据库，并下载或更新原始图标、来源和许可证说明，无需等待客户端发版。日文与汉化培育共用一次检查，服务地址默认为 `https://mag.2j.hk`。偶像任务配置、战斗 HUD 模板、流水线和模型仍随客户端版本更新。

## 客户端行为

安装包在 `data/` 内置偶像卡配置和 Buff／姿态模板配置，并在 `data/bundled/` 保存两个统一数据库、来源说明、数据许可证和数据库校验清单。首次启动会校验并事务安装到 `data/`；已有安装清单时沿用当前数据库。缺少或损坏的数据库会提示执行更新任务。快速模式沿用原有识别，完整模式可通过更新任务获取原始图标。

支援卡识别直接读取 `produce_reward_items.json` 的 `support_cards`，日文名称和插件中文名共同参与匹配。新安装可直接使用内置数据库；旧数据库缺少该字段时会提示更新。支援卡名称通过游戏 ID 合并，星数和识别结果导出格式沿用既有处理。

首次缺少图库时下载完整 ZIP。已有图片按 SHA256 复用，之后只下载新增、变化或损坏文件；变化文件达到 256 个或增量大小达到整包大小时使用整包，避免大量小文件请求。手工放入的上游原图同样参与复用。

同版本清单通过服务端声明的大小和 SHA256 校验后直接复用，正常无变化只请求一次版本入口，仍会在本地逐文件核验并发现损坏文件。普通日志每两秒汇总进度，并在完成时输出结果；逐文件名称仅写入 debug，失败文件仍明确提示。

正式数据继续放在 `data/`，图片直接位于 `data/images/skillCards/*.png`、`data/images/pDrinks/*.png`、`data/images/pItems/*.png`，不要再套 `icons/`。源码运行对应 `assets/data/`。更新不会改变图片像素、文件名、普通／强化版或偶像变体。

打包及同步 beta 时，`data/` 直接复制 `idols_cards.json`、`battle_buff_templates.json`，初始数据库及其清单复制到 `data/bundled/`。更新任务安装过的数据库、资源清单和图标保留在 `data/`，客户端升级时继续使用。客户端构建使用新的输出目录，按白名单复制数据。源码运行对应 `assets/data/`，下载和构建产物不提交。

下载、续传文件、解压暂存和覆盖前备份位于 `temp/produce_update/<资源版本>/`。文件全部校验后才安装；安装成功后删除本次临时目录，正式目录只增加 `produce_resources_manifest.json` 和来源说明。不会创建多份正式版本目录，也不清理 MFA 的其他临时文件。

更新失败时保留现有资源，已有有效数据库可继续完整模式；首次安装未完成时需重试更新。断点文件可供下次续传。只删除上次成功清单管理、且新版移除的文件，其他手动文件保留。更新过程中取消任务会停止后续操作。存在活动培育会话时跳过更新；成功后清除内存图库缓存，同一 Agent 的下一轮直接生效。

覆盖期间短暂保存 `data/produce_resources_pending.json`。启动及完整模式培育入口先检查它，恢复未完成的安装；如果备份被外部清理且正式文件不完整，禁止进入完整模式，需重新执行更新在线修复。修复失败时不能继续使用混合版本。快速模式不读取这些识别资源，跳过培育入口的数据库检查。成功恢复／修复后标记自动删除。

MFA 的 [AppPaths](https://github.com/MaaXYZ/MFAAvalonia/blob/master/MFAAvalonia/Helper/AppPaths.cs) 使用安装目录下的 `temp/`；[MaaProcessor](https://github.com/MaaXYZ/MFAAvalonia/blob/master/MFAAvalonia/Extensions/MaaFW/MaaProcessor.cs) 当前只清理 `temp_mfa`、`temp_maafw`、`temp_res` 专用目录。培育更新使用独立子目录，并额外防御整个临时目录被手工清空的情况。

测试或迁移地址可创建 `config/produce_resources.json`：

```json
{
    "base_url": "https://mag.2j.hk"
}
```

生产地址必须使用 HTTPS；本地测试允许 `http://127.0.0.1:<端口>`。配置不存放凭据。更新代码在 `agent/produce/resources.py`，随 Agent 打包；客户端不依赖 `tools/` 或 Pillow。

## 云端部署

1. 在 Cloudflare 创建 Standard R2 Bucket，默认名 `maagakumasu-produce-resources`。Bucket 保持私有，不启用 `r2.dev`；Worker 通过绑定读取文件。
2. 将 `2j.hk` 域名接入同一 Cloudflare 账户。为发布创建仅允许访问该 Bucket 的 R2 读写凭据。
3. 在 GitHub 仓库 Variables 配置 `CLOUDFLARE_ACCOUNT_ID`；Bucket 改名时额外配置 `PRODUCE_R2_BUCKET`。Secrets 配置 `R2_ACCESS_KEY_ID`、`R2_SECRET_ACCESS_KEY`。
4. 在 `cloud/produce-resources/` 执行 `npx wrangler@4 deploy`。`wrangler.jsonc` 已绑定 `mag.2j.hk` 和默认 Bucket，使用其他 Bucket 时同步修改配置。部署使用维护者自己的 Cloudflare 登录或 `CLOUDFLARE_API_TOKEN`，不把密钥写入仓库或客户端。
5. 先把工作流文件放到默认分支，让 GitHub Actions 显示 `Run workflow` 按钮。开发阶段运行 `Publish produce resources` 时，分支选择 `decision-capture`；该分支包含完整构建工具，main 暂时只有工作流入口。首次可手工填写上游完整小写 SHA，也可留空使用 `master`。当前暂不启用定时触发，功能完整合并到默认分支后再启用每日北京时间 08:00 检查。
6. 访问 `https://mag.2j.hk/v1/latest.json`，再下载对应清单和整包，核对客户端日志中的版本与哈希。用真实国内网络测试下载后再向用户开放。

资源发布使用独立工作流。客户端安装工作流先通过 `--databases-only` 构建一份初始数据库，供全部平台共用；原始图库由更新任务下载。Actions 的 Pillow、boto3、PyYAML 仅用于维护构建。域名、Bucket 和 Secrets 配置完成前，网络更新会失败，客户端可以继续使用已有数据库。

## 发布协议与维护

Actions 从上游 `gakumas-tools/gakumas-tools` 的同一固定提交读取 `packages/gakumas-data/csv/` 及 `packages/gakumas-images/images/{skillCards,pDrinks,pItems}/icons/`。CSV 按上游规则转换：`TRUE`／`FALSE` 转为布尔值，纯数字转为整数，其余保留字符串，再生成客户端 JSON 数据库。只选原始 PNG，不使用 `gk-img` 的缩小 WebP，不包含详情大图。数据许可文件和来源说明随包保留。

工作流同时检出 [游戏原文表](https://github.com/vertesan/gakumasu-diff) 和 [插件汉化表](https://github.com/chinosk6/GakumasTranslationData/tree/main/local-files/masterTrans)，记录各自实际提交与文件 SHA256。`game_revision`、`translation_revision` 可指定完整小写提交 SHA，留空使用各仓库的 `main`。回退时三个来源版本输入均留空。

汉化直接写入两个现有数据库。`name` 保留日文，`name_zh_cn` 保存插件中文名，`aliases` 保存中文及已核验的日文写法。`game_keys` 保存来源表与游戏 ID，只有技能卡附带 `upgradeCount`。H.I.F 自定义道具从 `ProduceCustomizeItem` 按名称和流派关联；支援卡从 `SupportCard` 按游戏 ID 合并，存入 `produce_reward_items.json` 的 `support_cards`。名称关联先精确匹配，再处理符号和小范围写法差异；缺少翻译或存在歧义时保留原条目，并在来源说明的 `translations.coverage` 中列出未关联 ID。

翻译表、原文表和关联代码都参与源内容指纹。汉化单独变化会触发重新构建，完整包与增量下载共用新增字段。中文名称可以用于查库，带心形等符号的完整名称优先匹配；同名且无法区分的多个身份仍保留未知。数据库名称对应的覆盖率与汉化版各页面的实机识别覆盖率分别验证。

校验包括数据结构、重复 ID、PNG 解码及尺寸、文件 ID 对应关系；缺图记录在来源说明的覆盖统计中。源内容指纹不变则跳过发布。数据库的下载时间固定为上游提交时间，避免仅因每天运行而产生新版本。

| 接口 | 内容 |
| --- | --- |
| `/v1/latest.json` | 协议版本、资源版本、清单大小与 SHA256 |
| `/v1/releases/<版本>/manifest.json` | 来源、文件路径／大小／SHA256、完整 ZIP 信息 |
| `/v1/releases/<版本>/full.zip` | 初始完整包 |
| `/v1/objects/<SHA256>` | 增量文件 |

资源版本由规范化文件清单的 SHA256 决定。上传并校验所有不可变对象后，最后替换最新版指针；Worker 使用内容哈希作为 HTTP ETag，支持 GET、HEAD、条件请求及单段 Range。普通 GET 只执行一次 R2 get，同次读取返回元数据和正文；HEAD 只读取元数据，断点续传保留额外的元数据与版本一致性检查。最新版响应要求重新验证缓存，固定版本文件长期缓存。

保留最近 14 个云端版本及其引用对象。回退时手工运行同一工作流，在 `rollback` 填资源版本，`revision` 留空；仅切换最新版指针，不改写旧版本。客户端不按版本号大小拒绝回退，会根据清单逐文件修复。

本地构建（输出放实验目录）：

```powershell
python tools/build_produce_resources.py --source <固定提交的上游检出目录> --output ../MaaGakumasuLab/debug/produce-resource-build
python tools/build_produce_resources.py --source <上游检出目录> --game-source <gakumasu-diff检出目录> --translation-source <GakumasTranslationData检出目录> --output ../MaaGakumasuLab/debug/produce-resource-build-zh
python tools/build_produce_resources.py --source <上游检出目录> --game-source <gakumasu-diff检出目录> --translation-source <GakumasTranslationData检出目录> --databases-only --output ../MaaGakumasuLab/debug/produce-databases
node --test cloud/produce-resources/worker.test.mjs
```

构建使用新的空输出目录。数据库打包模式只需检出上游 CSV；生成后将 `payload/` 中的文件放入 `assets/data/bundled/`，再运行 `tools/install.py`。CI 自动完成这两步。该模式供客户端打包使用，完整云端资源仍通过独立发布工作流更新；部署后检查资源接口与客户端下载。
